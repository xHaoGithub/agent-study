# 12 个里程碑学习路线

建议每个里程碑用 60–90 分钟。不是按“看了多少”完成，而是按“能交付什么、能解释什么”
完成。完整走完后，你会有一个可演示项目、一套评测结果和一份能用于面试讨论的系统设计。

[《AI Agents in Depth》第 1 章](https://bojieli.github.io/ai-agent-book/book/chapter1/#agent)

Calling、ReAct、Workflow、Harness、Guardrails 与评测思想映射到本项目。尤其在里程碑
0、5、6、7、9 学习时，必须回到该映射和原文完成对应任务。

学习记录使用 `../learning/LEARNING_RECORD.md` 中的 U01–U12 单元编号。里程碑提供实践顺序，

## 里程碑 0：先判断该不该做 Agent

练习：

1. 把需求拆成“必须确定”和“允许模型判断”两列。
2. 分别写出纯规则、固定工作流、有边界 Agent 三种方案。
3. 给每种方案评估错误代价、可解释性和开发成本。

通关问题：

- Excel 导出动作本身为什么不需要模型？
- 从一段访谈里提取事实为什么可以使用模型？
- 最终立项为什么不能让模型决定？

## 里程碑 1：大模型基础与选型

产出一张模型选型卡：

| 任务 | 候选 | 质量要求 | 时延 | 成本 | 上下文 | 工具调用 | 选择 |
|---|---|---:|---:|---:|---:|---:|---|
| 事实抽取 | 普通/小模型 | 高 | 低 | 低 | 中 | 否 | 待实验 |
| 多证据规划 | 推理模型 | 很高 | 可稍高 | 中高 | 大 | 是 | 待实验 |
| 分类路由 | 小模型/规则 | 中 | 很低 | 很低 | 小 | 否 | 待实验 |

必须用同一批 Golden Cases 比较，而不是各挑一个“好看案例”。

## 里程碑 2：Prompt 与上下文工程

在 `prompts.py` 中找到：

- 身份
- 目标
- 工具规则
- 禁止事项
- 何时澄清
- 异常处理
- 输出格式

实验：

1. 删除“资料不等于指令”规则，运行注入测试。
2. 恢复规则并新增一个注入案例。
3. 改 Prompt 后把 `PROMPT_VERSION` 从 `v1.0.0` 升到 `v1.1.0`。
4. 对比相同测试集，不凭单次回答决定好坏。

## 里程碑 3：JSON Schema

给 `priority` 增加 `owner` 字段。你必须同步：

- `ANSWER_SCHEMA`
- Mock 输出
- 真实模型 Prompt 语义
- `validate_answer`
- CLI 展示
- Golden Dataset

这样你会理解：结构化输出是模型与应用之间的“接口合同”，不是让回答看起来整齐。

## 里程碑 4：RAG

完成三组对照：

1. `top_k=1` 与 `top_k=8`：比较召回和噪音。
2. 大 Chunk 与小 Chunk：比较证据完整性和定位精度。
3. employee 与 admin：确认权限过滤发生在模型之前。

为每次失败标记：

- Retrieval miss：需要的证据没回来。
- Retrieval noise：回来的是错误/低相关证据。
- Grounding failure：证据回来了，但模型没有正确使用。

## 里程碑 5：工具调用

新增 `estimate_interview_effort(interviews, minutes_each)` 只读工具。

要求：

- 名称和描述让实习生也能正确使用。
- 参数用 JSON Schema，禁止额外字段。
- 数值校验放在代码，不依赖模型。
- 至少有正常、边界、错误三类测试。
- Golden Dataset 检查“该调用时调用、不该调用时不调用”。

## 里程碑 6：Human-in-the-loop

把“导出 CSV”设计成写工具，分别定义：

- 哪些参数执行前展示给用户。
- 什么角色有权批准。
- 拒绝后 Agent 怎么继续。
- 超时后状态是什么。
- 重试会不会重复写入。
- 怎么提供幂等键与撤销/回滚。

## 里程碑 7：Agent 与 Trace

选一个 `run_id`，从 `logs/traces.jsonl` 还原：

```text
用户输入 → 检索哪些 Chunk → 模型第几轮要求什么工具
→ 工具参数/结果 → 最终状态 → 总时延
```

然后制造三种错误：检索为空、工具参数非法、循环超过上限。为每种错误写恢复策略。

## 里程碑 8：AI 交互

设计一个不是“只有聊天框”的界面，至少包含：

- 模糊目标输入与示例
- 可编辑计划
- 检索/执行进度
- 工具确认卡片
- 中间结果修改
- 暂停、继续、取消
- 失败重试与恢复
- 证据抽屉
- 用户纠正和原因标签

原则：只在用户能作出有意义选择时追问；否则标记假设并继续。

## 里程碑 9：评测

把 5 条 Golden Cases 扩到 20 条，至少覆盖：

- 正常任务
- 模糊任务
- 无证据
- 冲突证据
- 越权访问
- Prompt Injection
- 工具该调/不该调
- 参数缺失/非法
- 写操作批准/拒绝
- 模型拒绝或超时

不要把 LLM-as-a-Judge 当唯一裁判。能用规则验证的字段、引用、工具、权限先用确定性检查。

## 里程碑 10：数据分析

从 Trace 计算：

- `completed / all_runs`
- `successful_tool_calls / requested_tool_calls`
- `denied_writes / requested_writes`
- 模型轮次平均值
- P50/P95 时延
- 每个 Prompt 版本通过率

再做错误 Pareto：先修复数量最多且业务损失最大的错误类型。

## 里程碑 11：上线设计

你的 V1 方案必须回答：

- 哪些用户先灰度？
- 使用哪个模型，为什么？
- 单任务最大 Token、工具次数、时长和成本是多少？
- 知识权限从哪里来，何时更新和失效？
- 哪些操作必须确认，谁能批准？
- 哪些指标触发降级、熔断或回滚？
- 如何保存用户纠正，但不收集不必要的敏感信息？
- Prompt、模型、知识库变化如何做版本回归？

通过标准：别人能根据你的文档判断“什么时候系统应该自动继续，什么时候必须停下来找人”。
