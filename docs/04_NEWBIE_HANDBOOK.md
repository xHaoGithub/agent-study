# 新手概念手册：把术语映射回这个项目

## 1. 大模型基础

### Transformer

可以先把 Transformer 理解成一套“根据上下文判断哪些信息值得关注”的网络结构。它并不是
数据库，也不是先查到唯一正确答案再复述；它根据训练中学到的模式，逐步预测后续 Token。

产品含义：语言流畅不等于事实正确，所以企业知识要通过 RAG 提供，关键计算交给工具。

### Token

Token 是模型处理文本的基本片段，不完全等于一个汉字或一个英文单词。输入 Prompt、历史
对话、检索文档、工具定义和输出都会占 Token。

产品含义：上下文越多，不一定越好；会增加成本、时延和噪音。项目用 `top_k` 控制进入模型的
Chunk 数量。

### Embedding

Embedding 把文本、图片等内容映射成一组数字，使“语义相近”的内容在向量空间中距离更近。
它常用于语义检索，不直接生成最终答案。

当前项目先用 BM25 关键词检索，因为更容易看懂和调试。里程碑 4 再加入 Embedding，做混合
检索对照。

### 预训练、SFT、偏好优化

- 预训练：从海量数据学习语言、知识和模式，是基础能力来源。
- SFT：用高质量“输入—理想输出”示例教模型更符合特定任务。
- RLHF/偏好优化：让模型输出更符合人类偏好、安全和风格。

产品经理通常不训练基础模型，但要能判断：问题是知识缺失、指令不清、工具不会用，还是模型
本身能力不足。前三种往往先用 RAG、Prompt、工具和评测解决。

### 上下文窗口与长文本

上下文窗口是单次请求能让模型共同考虑的信息容量。长文本不是直接全部塞入：

1. 解析和清洗。
2. 分成 Chunk。
3. 检索最相关部分。
4. 必要时重排序或摘要压缩。
5. 保留来源和版本。

截断最旧消息也可能丢失关键规则，所以长期规则应稳定、精简，并在每次请求明确提供。

### Temperature 与 Top-p

- Temperature 越高，采样通常越发散；越低通常越稳定。
- Top-p 只在累计概率质量内采样。

通常只调整一个。事实抽取、分类和工具参数偏向稳定；创意发散可以更随机。推理模型对这些参数
的支持可能不同，上线前按所选模型文档和评测确定，不能照搬固定“万能数值”。

### 幻觉为什么产生

- 模型目标是生成合理后续文本，不是保证事实来自数据库。
- 输入缺信息，模型仍可能按常见模式补全。
- 检索没找到、找错，或模型没有正确使用材料。
- Prompt 把假设写得像事实。
- 长上下文里证据被噪音淹没。

本项目的对策是引用、缺失数据字段、RAG、工具、结构化输出和回归评测；它们降低风险，不可能
把幻觉“彻底消灭”。

### Prompt、RAG、微调各解决什么

| 手段 | 主要解决 | 不擅长 |
|---|---|---|
| Prompt | 任务、边界、步骤、格式 | 注入大量动态企业知识 |
| RAG | 可更新、可授权、可引用的外部知识 | 稳定改变模型基础行为 |
| 微调 | 固定风格、分类边界、复杂工具习惯 | 实时更新事实和权限 |

顺序建议：先明确任务和评测 → 优化 Prompt/Workflow → 加 RAG/工具 → 数据足够后再判断微调。

### 多模态

多模态模型可以处理文本、图片、语音或视频。产品设计仍要拆清：

- 输入模态：用户给什么。
- 理解任务：OCR、分类、问答还是视觉推理。
- 输出模态：文本、语音、图片还是结构化数据。
- 证据与权限：图片和录音同样可能含敏感信息。
- 评测：不同模态需要不同数据集和质量指标。

### 普通模型、推理模型和小模型

| 类型 | 优势 | 代价 | 适合 |
|---|---|---|---|
| 小模型 | 快、便宜 | 复杂任务能力较低 | 路由、分类、抽取、批量任务 |
| 普通对话模型 | 语言和通用任务平衡 | 深度规划有限 | 总结、改写、常规问答 |
| 推理模型 | 多步规划、复杂约束更强 | 时延与成本可能更高 | 复杂分析、工具编排、难题 |

正确做法不是“永远选最强”，而是同一测试集比较成功率、时延和单成功任务成本。

## 2. 模型 API 基础

真实模式在 `model.py` 里做了四件事：

1. 向 `/v1/responses` 发 HTTP POST。
2. 用 `Authorization: Bearer ...` 鉴权。
3. 请求体是 JSON，包含 model、instructions、input、tools、text.format。
4. 解析 HTTP 错误、网络错误、模型消息和工具调用。

Function Calling 不是模型真的执行 Python。模型只返回“我想调用哪个工具、参数是什么”；
应用校验并执行，再把结果回传给模型。

## 3. Prompt 与上下文工程

### 消息角色

- Developer/System：应用提供的长期业务规则，优先于用户任务。
- User：本次目标、数据和临时要求。
- Assistant：模型历史输出，不自动变成最高优先级规则。

当前项目把稳定 Prompt 放在代码中，使用版本号和测试管理变更。

### 完整 Agent 指令检查表

在 `DEVELOPER_INSTRUCTIONS` 里逐项寻找：

- 身份
- 目标
- 可用工具
- 工具决策规则
- 禁止事项
- 异常处理
- 何时澄清
- 输出 Schema

Few-shot 示例不是越多越好。只有当错误模式稳定出现、简单规则仍不足时，才加入代表性示例；
加入后必须跑同一测试集。

### 上下文选择与压缩

上下文优先级可按：

1. 安全和业务规则
2. 当前用户目标
3. 当前任务必需的证据
4. 近期对话状态
5. 可丢弃的背景信息

把所有历史和文档都塞进去，会使重要信息更难被模型注意。

### Prompt Injection

`knowledge/04_untrusted_import.md` 中故意有恶意指令。防线不只是一句 Prompt：

- 资料和指令使用不同边界标签。
- 权限过滤在模型之前。
- 工具执行由应用控制。
- 密钥不进入上下文。
- 测试集持续包含攻击样例。

## 4. RAG 与知识库

RAG 链路：

```text
文档 → 解析/清洗 → Chunk → 建索引 → 查询 → 权限过滤
→ Top-K →（可选重排序）→ 放入上下文 → 生成带引用答案
```

三类常见失败必须分开统计：

- 没检索到：召回问题。
- 检索错：相关性/权限/版本问题。
- 检索对但没用好：Prompt、上下文或模型问题。

知识库产品规则：

- 只放业务上允许被回答、有人负责维护的内容。
- 每份资料要有来源、版本、权限、更新时间和失效策略。
- 回答引用 Chunk，不只引用“某个大文件”。
- 权限变更应尽快使旧索引失效。
- 检索失败策略由风险决定：低风险可澄清，高风险应拒答或转人工。

## 5. Agent 系统设计

Observe–Plan–Act–Reflect 可以翻译为：

- Observe：读目标、角色、证据和当前状态。
- Plan：判断下一步是回答、检索、计算还是请求确认。
- Act：调用被允许的工具。
- Reflect：检查结果，失败则修正或停止。

当前代码把“Reflect”限制成有限循环和最终校验，不让它无限自我反思。

### 单 Agent 与 Multi-Agent

先用单 Agent，当出现以下可测问题再拆分：

- 不同领域 Prompt 互相冲突。
- 工具太多导致选择准确率显著下降。
- 可并行子任务确实能降低总时延。
- 需要独立权限或责任边界。

多 Agent 会增加通信、上下文、时延、成本和调试难度，不是成熟度勋章。

### MCP 与 A2A

- MCP：标准化 Agent/模型如何发现和调用外部工具、资源。
- A2A：面向 Agent 之间任务委派、状态和结果交换的协议概念。

选择协议前先问：是否真的需要跨系统复用、权限和发现机制？只有两个本地函数时，直接 Function
Calling 更简单。

## 6. AI 交互与体验

完整任务体验不是聊天框，而是：

```text
目标输入 → 计划 → 执行进度 → 工具确认 → 结果
→ 用户修改 → 证据追溯 → 反馈 → 继续/暂停/恢复
```

追问规则：

- 缺失信息会改变安全边界或核心结果：先问。
- 可以用明确假设继续且结果可逆：标记假设后继续。
- 用户无法理解问题或没有信息：不要机械追问，给出获取信息的方法。

确认卡片应展示动作、对象、关键参数、影响范围、是否可撤销，而不是只问“确定吗？”

## 7. 评测与数据

Golden Dataset 至少包含：

- 用户问题
- 用户角色
- 标准答案或关键事实
- 证据文档
- 预期工具
- 禁止说法
- 预期状态

自动评测优先验证可确定的内容：Schema、引用、权限、参数、工具结果。主观质量再用人工或
LLM-as-a-Judge。Judge 会受提示词、顺序和自身偏差影响，因此要用人工样本校准。

错误分析不要只写“模型不好”，而要分到可行动根因：

- 数据/标注
- 解析/Chunk
- 召回/排序
- Prompt/上下文
- 模型能力
- 工具描述/参数
- 权限/审批
- 后端超时/异常
- UX 表达

你在这个项目中实际接触：

- HTTP 与 Bearer 鉴权：`model.py`
- JSON 与 JSON Schema：`prompts.py`
- Python 模块、类型、异常：`pm_agent/`

- 日志与错误码思维：`trace.py`
- 并发概念：当前为了安全关闭并行工具，后续可做对照实验
- Git：每个里程碑做小提交，Prompt 版本和测试一起变更
- 部署：V1 再加入服务层、环境变量、健康检查和监控

你的产品岗位通关标准不是能默写代码，而是能读懂接口、发现风险、提出可测试验收条件，并能
亲手改出一个小原型。
